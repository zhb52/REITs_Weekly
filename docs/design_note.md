## 第一部分　任务定义

### 1.1 目标用户与现状流程

**用户**：一名覆盖公募 REITs 的卖方研究人员（也就是作者本人）。

**现状流程**（每期约 4–6 小时，几乎全部手工）：

1. 从金融终端导出全市场行情与成交，另从基金公告整理除息与分红
2. 在 Excel 里算板块等权收益、P/NAV 分布、成交与换手
3. 重画四张图（指数走势、跨资产对比、分板块成交额、分板块换手率）
4. 按固定章节写 13 节分析文字
5. 排版成 Word，核对表、文、图三处数字是否一致
6. 存档，下周重复

**这套流程的真实痛点不是写作，是口径。** 2026-W45 期的三个实例：

| 问题 | 表现 | 后果 |
|---|---|---|
| 板块归属漂移 | 国泰海通济南能源供热 REIT（508087）在第一章按"能源"计算板块收益，在 1.5 的 P/NAV 表按"水利"计算 | 同一份报告里同一只基金属于两个板块；水利 P/NAV 中位数出现 1.284 与 1.430 两个版本 |
| 换手率三数不一致 | 底稿记 0.36%、正文写 0.31%、按 `Σ成交额÷Σ流通市值÷交易日数` 复算为 0.327% | 三个数互不相符，且 0.31% 用现有数据无法复现 |
| 单位陷阱 | 终端导出的"本周涨跌幅（%）"实际存的是小数（`0.0094637` 表示 0.95%） | 若直接入表，全部涨跌幅缩小 100 倍 |

这三类问题的共同点是：**单看任何一张表都发现不了**，必须跨表勾稽才能暴露。人眼做不到每期都查，脚本可以。

### 1.2 任务规模与递归性

- **周期**：每周一期，报告期为周一至周五，基准日为上周五收盘
- **单期工作量**：96 只有效样本、13 个分析小节、5 张表、4 张图、约 5,400 字
- **递归触发**：每周五收盘后数据更新即触发；另有"新输入到达"触发（终端导出文件更新）
- **复用性**：章节结构、口径规则、图表样式、写作范式在期与期之间完全一致，只有数据在变

### 1.3 阶段划分与依赖

```
取数 ──> 归一化 ──> 计算 ──> 事实库 ──┬──> 图表 ──┐
                                      └──> 草稿 ──┴──> 门禁 ──> 人工审批 ──> 出稿 ──> 质检
```

依赖关系是**单向**的，只有一处回边：门禁不通过时回到草稿修订，修订轮次上限 2 轮。

| 阶段 | 输入 | 输出 | 依赖 |
|---|---|---|---|
| 取数 | 数据源适配器 | 原始表 | 无 |
| 归一化 | 原始表 + 板块字典 | 规范表（含 `board`、`asset_class`） | 取数 |
| 计算 | 规范表 | 指标（收益、广度、估值、流动性） | 归一化 |
| 事实库 | 指标 | `facts.json`（带 `fact_id` 与 `display`） | 计算 |
| 图表 | 指数序列、分板块成交 | 4 张 PNG | 计算 |
| 草稿 | 事实库 + 上一期观点 | 13 节文本（含占位符） | 事实库 |
| 门禁 | 草稿 + 事实库 + 全体规范表 | 7 条门禁结果 | 草稿 |
| 出稿 | 草稿 + 表 + 图 | `docx` | 门禁 + 审批 |

### 1.4 输入、允许来源与信息截止

**输入清单**：个券周度行情（收盘价、成交额、流通市值、总市值、P/NAV）、分红除息记录、指数日序列、利率序列、一级市场事件、解禁与持有人变动披露。

**允许来源**（白名单，见 `config/sources.yaml`）：

| 来源 | 用途 | 许可 |
|---|---|---|
| 妙想 MCP（东方财富） | 个券行情、成交、单位净值、流通份额 | 公开市场数据 |
| 沪深交易所公示 | 上市、审核状态、解禁、权益变动 | 公开披露 |
| 中证指数公司 | 指数点位与日序列 | 公开 |
| 中国债券信息网 | 国债收益率、DR007 | 公开 |

**明确禁止**：任何未公开的客户数据、内部研报、付费终端的非公开字段。示例数据（`fixtures/`）只保留公开行情字段，剔除内部批注与来源编号，因此可以随作业公开。

**信息截止**：报告期最后交易日 15:00 收盘定价；公告与事件截至报告期结束后的周日 23:59。**晚于该时点的信息一律不得进入本期结论**——这是"防止未来信息泄漏"的具体落点，由门禁 `G-PIT-01` 强制执行。

### 1.5 工作产品与验收标准

**工作产品**：一份 `.docx` 周报，含摘要（3 小节）、两章正文（10 小节）、风险提示、5 张表、4 张图；以及配套的 `facts.json`（本期全部数字及其来源）、`gates.json`（质检结果）、`state.json`（运行状态）。

**验收标准**分两层：

*可判定的（由门禁自动执行）*

1. 正文每个数字都能映射到事实库中某条记录的 `display`（`G-NUM-01`）
2. 板块样本数之和 = 全市场可比样本数；涨+跌+平 = 样本数；板块成交额之和 = 全市场成交额（`G-NUM-02`）
3. 数值落在合理量级，防止单位错误（`G-UNIT-01`）
4. 同一基金代码在全篇只属于一个板块（`G-BOARD-01`）
5. 所有事实的数据时点不晚于信息截止（`G-PIT-01`）
6. 章节齐全、风险提示只出现一次、数据缺口已显式标注（`G-STYLE-01`）
7. 仓库内无凭证（`G-SRC-01`）

*需要判断的（由 Critic 与人工执行）*

8. 论证是否成立：结论是否有证据支撑，事实与推断是否分清
9. 口径是否声明：板块等权、市值加权、指数全收益三类口径是否分别命名
10. 与上期观点是否衔接：判断是维持、强化、削弱还是撤销

### 1.6 为什么必须是常驻工作流，而不是一次性脚本

四个理由，每一个都对应一类一次性脚本无法处理的情况：

1. **口径需要跨期一致**。板块字典、样本纳入规则、换手率公式必须每期相同。脚本可以硬编码，但一旦数据源改变分类（如终端把 508087 归到水利），硬编码就静默失效。工作流把口径放在配置里，并让门禁在漂移时报错。
2. **必须能中断续跑**。一期跑完要几分钟到几十分钟，中途可能因数据缺失、网络中断、人工离开而停下。一次性脚本重跑要全部重来；工作流记录检查点，恢复时只做未完成的部分。
3. **必须能验证改动**。写作提示词、图表样式、章节结构都会迭代。改动是否让结果变好，需要与固定基线对比。没有版本记录与回滚，每次修改都是赌博。
4. **必须能拦错**。数字错误在这类报告里的代价远高于写作质量——一个 0.31% 可以进入投资结论。只要流程是"人写完自己检查"，这类错误就一定会漏。工作流把检查变成独立的、可判定的、每次都跑的步骤。

## 第二部分　架构设计

### 2.1 角色与交接

| 角色 | 职责 | 工具 | 输入产物 | 输出产物 | 是否可用 LLM |
|---|---|---|---|---|---|
| 数据适配器 | 取数并附溯源 | 妙想 MCP / 交易所抓取 / 本地 CSV | 期次参数 | 规范表 + `SourceMeta(raw_hash)` | 否 |
| 归一化 | 板块映射、单位归一、样本分类 | `config/boards.yaml`、`fund_registry.csv` | 原始表 | 含 `board` 的规范表 | 否 |
| 计算器 | 收益、广度、估值、流动性 | 纯函数（`compute/`） | 规范表 | 指标字典 | **否** |
| 事实库 | 给每个指标发 `fact_id`、定型 `display` | `facts.py` | 指标字典 | `facts.json` | 否 |
| 图表 | 四张图 | matplotlib | 指数序列、板块成交 | PNG | 否 |
| **起草者** | 按章节写分析文字，数字一律用占位符 | 草稿文件 + 事实库 | task packet（事实切片 + 写作要求 + 上期观点） | 13 节草稿 | **是** |
| **Critic** | 独立评审：逻辑、证据边界、口径、克制、连续性 | 只读事实库与草稿 | 草稿 + 评分细则 | 评分 + 问题清单 | **是**（独立上下文） |
| 控制器 | 推进阶段、跑门禁、重试、阻断、记录状态 | `controller.py` | 状态 + 产物哈希 | 新的 `state.json` | **否** |
| 人工 | 审批终稿；判定口径争议 | — | 门禁结果 + 草稿 | `approvals[]` | — |

**为什么这样切分**：

- **计算与写作分离**是最重要的一条。LLM 擅长组织论证，不擅长保证数字正确。把数字生产完全交给确定性代码，写作只负责引用，就从结构上消除了"模型算错一个数"这类风险。`G-NUM-01` 是这个设计的执行者：它反向扫描成稿里的每个数字，凡是不能映射到事实库的就报错。
- **Critic 与起草者分离**。同一个上下文里"自己检查自己"几乎无效——起草者会倾向于认为自己写对了。Critic 在独立上下文、只看产物与事实库，能发现起草者看不到的问题。但它也不是万能的：共享的前提错误（比如两边都误读了口径）仍可能同时存在，所以门禁与人工审批不可省略。
- **控制器不含 LLM**。流程推进必须可判定、可复现。如果让模型决定"这一步算不算完成"，验收标准就会随模型状态漂移。

**确定性代码的边界**：凡是有唯一正确答案的计算——收益、加权、分位数、汇总额、勾稽——一律由代码完成。凡是需要判断的——归因分类、观点表述、风险排序——才交给模型。

**agent 决策与执行控制的区分**：

| 事项 | 谁决定 |
|---|---|
| 这一节怎么写、举哪个例子 | 起草者（agent） |
| 某一版草稿是否可以接受 | Critic 打分 + 人工签字，**不是起草者** |
| 数字是多少 | 计算器（代码），起草者无权修改 |
| 能否进入下一阶段 | 控制器（依据门禁结果与产物哈希） |
| 门禁阈值是否放宽 | 人工（且需记录理由） |

### 2.2 长跑运行

**持久状态**。`cases/<期次>/state.json` 是唯一权威，包含三段：

- *身份*：`case_id`、`pipeline_version`、`input_hash`（输入数据的联合哈希）
- *进度*：当前 `stage`、`status`、各阶段尝试次数
- *证据*：每个产物的 `path` / `sha256` / `bytes` / `stage`，以及门禁结果、审批记录、完整流转历史

写入采用**原子替换**（先写 `.tmp` 再 `os.replace`）。半个状态文件比没有状态文件更危险，它会让续跑基于错误的前提。

**检查点与恢复**。每个阶段结束登记产物哈希。恢复时的判据是：

```
产物存在 且 sha256 与登记一致 且 登记的 stage 与当前阶段匹配  →  SKIP
否则                                                      →  REDO
```

实测：完整跑一期约 3 秒（示例数据），`--force` 与增量耗时差异体现在是否重算事实库与图表。

**重试与停止规则**：

| 情形 | 处理 | 是否自动重试 |
|---|---|---|
| 数据源超时、5xx | 指数退避 5s/20s/60s，上限 3 次 | 是 |
| 数据源 schema 变化（字段缺失） | 标记 `SchemaDriftError`，转 BLOCKED | 否 —— 需人确认新字段含义 |
| 草稿占位符无法解析 | 转 BLOCKED，列出未解析的指标名 | 否 |
| 门禁不通过 | 回到修订，上限 2 轮 | 是（有界） |
| 门禁连续 2 轮不过 | 转 ESCALATED，写 `escalation.md` | 否 |

三态终止的语义区别很重要：`BLOCKED` 是等外部条件（补数据、给权限），`FAILED` 是代码有 bug，`ESCALATED` 是额度或轮次用尽需要人决策。**耗尽配额永远不等于通过**——这是从课程案例里带过来的一条硬规则。

**上限**（`config/settings.yaml`）：单次运行墙钟 3600 秒、单阶段 600 秒、LLM 成本上限 3 美元、工具调用 300 次、单次适配器请求 30 秒。工具权限按角色限定：适配器只读输入目录，计算层不触网，起草者不能写 `facts.json`。

**触发方式**：定时（每周五 17:30 首跑，周六 10:00 复跑定稿）+ 手动（`cli run`）+ 新输入触发（`inputs/` 目录文件变更）。

### 2.3 验证与改进

**独立于产出方的检查**。Critic 只拿到三样东西：`facts.json`、草稿文本、上一期的 `opinions.yaml`。它看不到起草者的推理过程，也看不到草稿的中间版本，避免被锚定。

评分五个维度，各 1–5 分：逻辑链、证据边界、口径声明、克制（有无无据断言）、连续性（与上期观点的关系）。通过线为均分 ≥ 3.5 且无 high 级问题。

**有后果动作前的人工审批**。流程在门禁通过后**必然停下**，等待 `cli approve`。审批记录里绑定当时草稿文件的 `sha256`：

```json
{"gate": "HUMAN_REVIEW", "by": "周豪波", "decision": "approve",
 "artifact_sha256": "9f2c…", "at": "2026-11-14T03:02:11+08:00"}
```

如果审批之后草稿又被改动，哈希不再匹配，`has_approval()` 返回 False，出稿会被拒绝。这是"防止批完再偷偷改"的机制。

**有界修订循环**。门禁不通过 → 回到修订 → 重跑门禁，最多 2 轮。每次修订必须保留上一轮的问题清单，未解决的问题不能因为本轮没提就自动关闭——这在课程案例里叫 finding ledger，本项目用 `qa/gates.json` 的累积记录实现。

**改动如何测试、接受与回滚**：

- *固定基线*：`tests/` 中 88 项用例存放 2026-W45 期的数值断言与中断恢复场景。任何改动都要与基线比对。
- *对比方法*：`pytest` 断言关键指标与基线一致（94 只 / 41涨50跌3平 / P-NAV 1.055 / 1.091 / 56溢价38折价 / 成交 21.93 亿 / 换手率 0.327%）。若某项指标确实需要变，必须同时更新基线与 `CHANGELOG.md`，并说明理由。
- *版本记录*：`pipeline_version` 写入 `state.json` 与文档属性；每次口径变更在 `CHANGELOG.md` 留条目。
- *回滚*：代码层面用 `git revert`；数据/口径层面回滚 `config/` 并重跑，历史 `cases/` 目录不受影响（每期产物独立存放）。

**防止未来信息泄漏**。`verify/gates.py::point_in_time` 断言所有事实的 `source_asof` 不晚于 `info_cutoff`。注意这里是**与案例配置的截止时点比较，而不是与系统时钟比较**——否则回放历史期次时，所有数据都会被误判为"未来数据"。

### 2.4 已知边界与后续工作

诚实的边界比漂亮的完成度重要。目前仍有三项限制：

1. **Critic 是规则版，不是模型版**。五个维度用可解释的启发式打分（是否有证据、是否绝对化、是否声明口径等），优点是可复现、可审计、零依赖，缺点是无法判断"论证的实质是否成立"。接口已按模型版设计，替换 `_score_*` 即可，但目前的评分不能替代真人评审。

2. **一级市场数据靠公告转录，不是抓取**。`event_metrics.csv` 里的数字（发行规模、解禁比例、增持金额）是从公告原文摘录的，`formula` 标为 `announcement_transcription`，与计算型事实在溯源上区分开。待上市清单（47 只）则是结构化数据，可直接计算分布。要做到真正无人值守，还需接交易所公示页。

3. **原生图表未启用**。默认输出 300dpi PNG，牺牲了"在 Word 里继续编辑图表数据"的能力，换取版式稳定。样张的原生图表在数据点数变化时需同步修改 `c:ptCount`、`c:f` 与内嵌 xlsx，脆弱且易出错。

### 2.5 修订循环的实际效果

第 2.3 节描述的是设计，这里给出一次真实运行的结果作为佐证。首轮 Critic 均分 4.66，指出 2.5 节"多处判断但无不确定性表述""未交代与上期观点关系"。按意见修订三节后重跑：

| 章节 | 修订前 | 修订后 |
|---|---|---|
| 2.5 综合判断 | 3.6 | 4.6 |
| 0.3 配置关注 | 4.2 | 5.0 |
| 1.3 个券异动 | 4.4 | 5.0 |
| 全篇均分 | 4.66 | **4.85** |

修订前后记录保留在 `cases/demo-2026-W45/qa/critic.json` 与 git 历史中，可复核。
