# 修订指令

当 Critic 判定 `revise` 时，控制器把问题清单打包成 repair packet 交回 Writer。

## repair packet 结构

```json
{
  "section_id": "2.5",
  "round": 1,
  "findings": [
    {"id": "C-01", "severity": "high",
     "problem": "多处判断但无任何不确定性表述，事实与推断边界模糊",
     "evidence": "「估值有底、催化不足」为判断句，但后文未说明何种情况下该判断失效"}
  ],
  "required_evidence": [
    "补一句失效条件，例如「若 P/NAV 中位数连续两周上行且分化收窄，则该判断需要修正」"
  ],
  "carried_open_findings": []
}
```

## 三条硬规则

1. **只改被点名的章节**。不要顺手改别的节——那会让下一轮的对比失去意义，
   也让"这次改动是否真的解决问题"无法判断。

2. **未关闭的问题必须继续出现在下一轮的 `carried_open_findings` 里**。
   这一轮没提，不等于它已经解决。这是从课程案例里带过来的一条：
   第二轮漏提第一轮的 finding，那个 finding 仍然是 open 的。

3. **不得为了过关而稀释标准**。把"必然上涨"改成"上涨"不算修订；
   要改成"若供给节奏放缓，则可能上涨"才是修订——保留判断的锐度，
   同时给出成立条件。

## 修订轮次上限

2 轮。第 2 轮仍未通过则转 `ESCALATED`，由人决定是放宽标准还是改数据。
**耗尽轮次不等于通过**——这是本项目最不愿妥协的一条。
