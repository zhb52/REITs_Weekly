# 公募 REITs 周报 · 自动化生产工作流

> 复旦大学国际金融学院《AI Coding in Finance》期末项目（个人作业）
> 作者：周豪波　学号：25210660117　2026 年秋季

把"每周出一份公募 REITs 周报"从纯手工流程改造成**可长跑、可校验、可恢复、可迭代**的 agent 工作流。

**仓库地址**：https://github.com/zhb52/REITs_Weekly（完整开发历史同时包含在本目录的 `.git/` 中，无需访问远程即可审阅）

---

## 它解决什么问题

周报每期约 4–6 小时，绝大部分不是写作，而是数据整理与口径核对。真正的痛点有三个，
都来自 2026-W45 期的真实事故：

| 问题 | 表现 |
|---|---|
| **板块归属漂移** | 国泰海通济南能源供热 REIT（508087）在第一章按"能源"算、在 1.5 的 P/NAV 表按"水利"算。同一只基金在同一份报告里属于两个板块 |
| **换手率三个数** | 底稿 0.36%、正文 0.31%、按公式复算 0.327%，互不相符 |
| **单位陷阱** | 终端导出的"涨跌幅（%）"实为小数（`0.0094637` = 0.95%），直接入表会缩小 100 倍 |

这三类错误的共同点是**单看任何一张表都发现不了**，必须跨表勾稽。人眼做不到每周查，代码可以。

本项目的做法：数字全部由确定性代码产生，正文只允许用占位符引用；写完再由独立门禁
反向扫描每个数字能否回溯；跨章一致性、样本勾稽、信息时效各有一条硬门禁。

## 环境与运行

依赖**全部装在项目内**的 `.venv`，不影响系统环境。

```bash
# 一条命令完成：建 venv、装依赖、可编辑安装、跑测试
powershell -ExecutionPolicy Bypass -File scripts/bootstrap_venv.ps1
```

或手动：

```bash
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.in
./.venv/Scripts/python.exe -m pip install -e .
./.venv/Scripts/python.exe -m pytest -q      # 119 passed
```

### 跑一期

```bash
# 1. 跑完数据 → 计算 → 图表 → 草稿 → 门禁（会停在人工审批）
./.venv/Scripts/python.exe -m reits_weekly.cli run --case demo-2026-W45

# 2. 查看状态
./.venv/Scripts/python.exe -m reits_weekly.cli status --case demo-2026-W45

# 3. 审阅后签字
./.venv/Scripts/python.exe -m reits_weekly.cli approve --case demo-2026-W45 \
    --by 周豪波 --comment "数字已核，口径无异议"

# 4. 再次运行出稿
./.venv/Scripts/python.exe -m reits_weekly.cli run --case demo-2026-W45
```

第一条命令会返回 `[HUMAN_REVIEW] BLOCKED`，这是**设计如此**——门禁全过后流程必然停下等人签字。
成品在 `cases/demo-2026-W45/out/`。

依赖：Python ≥ 3.11、Git ≥ 2.40；Python 包见 `requirements.in`（python-docx、matplotlib、
pandas、numpy、PyYAML、openpyxl、lxml、requests、pytest）。中文字体优先宋体，缺失时降级雅黑并在质检中记录。

## 本人贡献

本项目从需求到交付由本人主导完成。AI 编码助手承担代码实现，研究判断、口径、环境与验收由本人负责。

**1. 需求解读与任务定义**

把课程要求拆解成可执行的规格：确定以本人日常产出的公募 REITs 周报为对象；界定单期范围（周一至周五、96 只样本、基准日取上周五收盘）；定下 13 个分析小节的章节结构与各自的写作要求；明确"什么算完成"的验收口径。

**2. 数据采集与整理**

提供并组织全部原始数据：金融终端导出的全市场行情、成交与 P/NAV，数据底稿，以及待上市储备清单。整理除息记录与利率序列；从既有周报的原生图表中提取四条指数各 1,234 个交易日的序列；整理本周一级市场、解禁、增持事件。同时判定哪些数据可用于报告、哪些不得使用。

**3. 口径制定**

报告里所有会改变数值的规则都由本人定：

- 换手率统一为 `Σ成交额 ÷ Σ流通市值 ÷ 交易日数`（原报告同一指标出现三个互不相符的数值）
- 508087 归入能源基础设施（原报告前后章节分类不一致）
- P/NAV 只用可比样本，新上市标的单列观察
- 板块收益用等权，与市值加权的官方指数分别命名，不得混用
- 全收益指数与价格指数的差额归因于分红，不另设口径

**4. 规则判定**

定义"数字可回溯"的具体含义：正文出现的每个数字都必须能映射到某条计算结果；同时划定例外边界（期限名称、指数代码、日期、章节号不在此列）。设定门禁的通过线与量级区间，以及"连续两轮不通过即转人工"的上限。

**5. 交付成果规范**

确定成品形态：版式（正文 11pt、首行缩进两字符、行距 1.15、标题配色）、五张表的结构与列宽、四张图的样式与配色、章节顺序与篇幅区间。这些直接决定成品能否直接使用。

**6. 工程环境与版本管理**

- 在本人 GitHub 账号下创建代码仓库 `zhb52/REITs_Weekly`，选择公开可见
- 生成并配置 SSH 密钥对，将公钥录入账号，使推送免密且不把凭证写入仓库
- 决定不勾选平台自动生成的 README、`.gitignore` 与 License，避免与本地既有内容冲突，并由本人确认课程作业不附开源许可
- 确立存储规范：所有依赖、产物与备份一律存放在项目目录内，不占用系统盘；交付物、过程依赖、备份分目录存放

**7. 质量把关与迭代推动**

过程中持续质疑进度与质量，直接改变了交付结果：

- 指出"开发过程要有有意义的提交"，避免了最后一次性提交
- 要求逐条对照作业原文核查，由此发现 `prompts/` 与 `skills/` 为空目录、断点恢复实际是空操作等问题
- 要求实际运行验证而非仅靠自查，暴露出事实库每次重写、产物无法逐字节复现的问题
- 对"是否已经完成"的追问，避免在仍有缺口时提前收尾

**8. 验收与定稿**

逐项核对程序输出与原报告（94 只 / 41涨50跌3平 / P-NAV 1.055 与 1.091 / 56溢价38折价 / 成交 21.93 亿），确认口径可复现；通读成品周报并确认内容可用；审阅每期草稿并签字发布，签字绑定草稿哈希；确立"数据缺口必须显式标注、不得以估算值填充"的底线。

**9. 代码实现**

数据层、计算层、门禁、状态机与文档装配的代码，由 AI 编码助手在本人指导下编写与调试。本人提出每项功能的需求与验收标准，对实现结果逐项确认，不参与逐行编码。

> 分工原则：**需要判断的由本人决定，需要环境与资源的由本人提供，需要编码的由助手实现，实现结果由本人验收。**
> 本项目按课程要求使用 AI 工具完成。

## 已知边界

- Critic 是规则版而非模型版：可复现、可审计、零依赖，但判断不了论证的实质成立与否
- 一级市场关键数值靠公告转录（`formula=announcement_transcription`），不是自动抓取
- 原生 Word 图表未启用，默认 300dpi PNG（换取版式稳定）

详见 `docs/design_note.md` 第 2.4 节。
