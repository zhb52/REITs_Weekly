# 数字落地协议（Number Grounding）

## 要解决的问题

报告里的数字有两个来源：算出来的，和"记得的"。后者是错误的主要来源——
模型可能记得一个过时的数值，或者自己心算一个差值，而这两者都无法核对。
本协议用占位符 + 运行时解析，从结构上消除"数字来源不明"的可能。

## 协议

### 写的时候

正文**不写阿拉伯数字**，只写占位符：

```
本周全市场成交额 {{M:turnover.total}} 亿元，环比 {{M:turnover.mom}}。
板块层面，产业园区 {{M:board.eq_return|board=产业园区}}、
数据中心 {{M:board.eq_return|board=数据中心}}。
```

### 语法

| 形式 | 用途 |
|---|---|
| `{{M:metric}}` | 唯一指标 |
| `{{M:metric\|key=value}}` | 带参数，用 `\|` 分隔 |
| `{{M:metric\|k1=v1\|k2=v2}}` | 多参数 |

参数值要与事实库里 `params` 完全一致，包括中文字符。

### 解析时

1. 按 `metric` 找候选
2. 按 `params` 过滤
3. 唯一命中 → 替换为 `display`
4. 零命中或多命中 → **抛错并阻断**，不静默留空、不填 0

多命中通常意味着参数不够。例如 `{{M:pnav.board.median}}` 有 10 个板块候选，
必须写成 `{{M:pnav.board.median|board=产业园区}}`。

## 为什么用可读指标名而不是哈希 ID

事实的 `fact_id` 是 `sha1(metric+params+case+input_hash)`，人和模型都无法在写稿时
知道它。要求作者填哈希等于强迫他猜，必然出错。可读名 → 运行时解析，才是可用的设计。

`fact_id` 仍然重要：它由输入派生，输入一变 ID 就变，旧引用会自动失效——
这保证了"口径变了，正文不会悄悄指向过期数值"。两者分工不同。

## 反向审计

替换完成后再做一次**反向扫描**：把成稿里所有裸数字抓出来，凡是不能映射到
某条事实 `display` 的就报错。

这一步抓的是"模型自己算的数"。例如文中写"首尾相差 5.8 个百分点"，
而事实库里没有 5.8 —— 说明这个数是模型心算的，必须改成引用两条事实，
或者把它登记成一条新事实。

## 允许的非事实数字

期限名称（10年期）、指数名（沪深 300）、日期、章节号、中文序数（第一类）。
除此之外一律要有出处。白名单只能因为"这类数字确实不是数据"而添加，
不能因为"加了就能过"而添加。
